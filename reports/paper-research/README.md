# 论文调研与网站发布规范

这是用户在 2026-10-18 确认的论文调研标准。基准为已确认满意的 [Pilot-Based 调研报告](../../posts/2026/10/18/pilot-based-radio-positioning-mapping.html)，对应源码为 [Markdown](../2026/2026-10-18-pilot-based-radio-survey.md)。后续以当前网站的公共组件为准，保留这些内容与可读性要求，不机械复制该论文的结论、公式数量或图片数量。

## 适用范围与默认交付

用于用户提供论文标题、链接或 PDF，要求精读、研究分析、调研报告，或要求“按之前的方式分析”的任务。一般短问答、单个公式讨论不必生成长报告。用户确认延续本次完整流程：中文调研、可维护源码、分类归档与 GitHub 网站发布；若当前请求仅要求讨论、草稿、本地保存或不发布，按当前请求执行。

网站是 `lucky-xing/lucky-xing.github.io`，线上地址 `https://lucky-xing.github.io/`。它不是 Sites 的“轻舟 AI 工作台”。不要创建替代网站，不要改变站点可见性。

## 内容验收标准

### 1. 原文与版本

先获取并通读可获得的完整论文，核实标题、作者、发表信息、DOI/arXiv ID 和实际阅读版本。优先使用作者、出版方、arXiv、学校等一手来源。预印本与正式版如有影响结论的变化，应说明。

不能以摘要、搜索摘要或二手介绍代替方法与实验阅读。若确实无法获取全文，交付能完成的部分并明确缺口，不能声称已完整精读。对结果和公式建立来源定位：章节、公式号、图号、页码；网页中以可点击链接呈现。

### 2. 详细问题建模

回答研究要解决的具体问题、输入、输出、已知量、未知量、状态变量、观测关系和关键假设。说明约束、噪声/不确定性以及适用场景。数学型论文必须用公式表达核心问题，解释符号、单位、维度及物理或算法意义。

例如通信论文应交代信号、信道、阵列、同步、路径等假设；机器学习论文应交代任务、模型、训练目标、数据与推理；优化论文应交代目标函数、约束和求解条件。按论文类型调整，不能强套无线模型。

### 3. 方法转换与求解链

逐阶段解释“原问题怎样转换成可求解的问题”。每一步交代：输入 → 表示/变换/目标 → 求解方式 → 输出 → 为什么这样做 → 失败条件。覆盖决定方法的关键公式，不只列概念名或贴公式。

区分原文公式、等价重写、报告自行推导和报告建议；标注原文公式号。对疑似符号笔误、单位或维度不一致，说明原文写法、整理理由与待核实点，不悄悄修改原文。不要从标题猜测方法，例如“端到端”不自动等于神经网络。

必要时增加流程图、符号表、输入输出表、伪代码或关键推导。数量由解释充分性决定，不规定至少 16 个公式等固定门槛。

### 4. 实验条件与效果

说明数据来源、场景、样本/试验次数、硬件或仿真、参数配置、指标定义和统计口径。区分定位与建图、训练与推理、平均与单次、准确率与删除率、仿真与实测，不能互换。

每个性能数字应能追溯原文；报告计算的比例要明确是自行计算并展示分母。论文没有报告的数值写“未报告”，不通过图片猜测精确数字，也不生成虚假实验或把拟议实验当作作者结果。

### 5. 结果原图与比较

有原文结果图时，报告必须展示与结论直接相关的原图，而不只是链接、文字或自制示意图。根据需要加系统、模型或场景原图。可以从可使用的公开版本提取，标注作者/论文、版本、图号/页码、来源链接和许可。尊重访问与许可限制；不能取得或不能合法展示时说明限制，不用 AI 重绘或伪造原文结果。

图片保留完整坐标轴、单位、图例、重要标记和原图注；不能裁掉不利结果。可以排除周围无关正文；图像内容不改动。白底科学图保留白底，不反色或染成网站主题。存本地资源，清晰可放大；配中文图注与逐项读图解释。

明确：比较的是哪些方法/变体/处理阶段；实验条件是否相同；改善是什么；代价、残留错误与不确定性是什么。结果表同时给出基线和本方法数据；缺少对照或消融就直说。相关工作能力差异不等于同条件性能胜出，删点比例不等于错误检出率或准确率提升，单次图不等于多次统计平均。不要宣称没有证据的 SOTA。

### 6. 评价与研究建议

评价创新点与实际证据是否相符，指出关键假设、局限、失败案例、复现缺口和工程代价。区分“作者结果”“读图观察”“本报告判断”“未来建议”。复现建议应给出有意义的消融、压力测试和指标，不能只写宽泛展望。

推荐文章结构见 [template.md](template.md)，允许按论文内容调整章节。

## 实现与网站风格

- 使用网站根目录 `style.css`、当前分类页的页眉/导航/页脚、`theme-motion.js`。不另起白底网站或重新设计品牌。
- 新报告使用共享 `assets/paper-report.css`，正文继承网站的 Inter / Microsoft YaHei / PingFang SC 无衬线字体，桌面正文 18px、中等字重；移动端 17px。标题不压缩字距；正文、表格、目录保持清晰对比，不能再出现深色背景配深色文字。
- 数学排版由本地 `assets/vendor/mathjax/tex-svg-full.js` 渲染；保留其 LICENSE。Markdown 行内使用 `$...$`，独立公式使用 `$$...$$`；公式不要当代码块。代码块中的美元符号应保留为代码。
- 长公式、宽表格在自己的容器内横向滚动，不能撑宽整个页面。原图宽度自适应，点击可查看原尺寸；图注清楚可读。
- 参考文章已使用 `assets/isac-reading.css`，保留其已确认样式；新增文章优先使用通用样式，避免为每篇论文再复制一套。

## 目录与生成

```text
posts/YYYY/MM/DD/<paper-slug>.html            发布文章
reports/YYYY/YYYY-MM-DD-<paper-slug>.md       可维护报告源
assets/papers/<paper-slug>/                  原图与来源说明
assets/paper-report.css                      共享阅读样式
assets/vendor/mathjax/                       本地公式组件
```

通感文章归入 `通信 → 通感`，栏目入口是 `communication/isac/index.html`；其他主题按研究对象归类，不把所有论文放进通感。更新栏目文章列表、计数、必要的父栏目入口、首页最新研究和 `ARTICLE-CATEGORIES.md`；保留旧文章和无关改动。

使用 Python 3、`Markdown` 和 `beautifulsoup4` 运行生成工具。它只生成文章和做静态检查，不执行 Git 推送、不代替内容研究、不会自动修改栏目列表。Markdown 中图片建议用站点根路径 `/assets/papers/<paper-slug>/...`，避免依赖文章目录深度。

```text
python scripts/render-paper-report.py render --source reports/2026/2026-10-18-example.md --output posts/2026/10/18/example.html --date 2026-10-18 --shell communication.html --category-label 通信 --category-url communication.html --section-label 通感 --section-url communication/isac/ --summary "一句话概括研究问题和贡献"
python scripts/render-paper-report.py check posts/2026/10/18/example.html communication/isac/index.html communication.html index.html
python scripts/check-paper-report-renderer.py
```

`--repo` 可在子命令前指定另一个仓库目录；更新已存在文章时显式增加 `--overwrite`。生成器复用当前分类页的公共组件、生成目录、保护代码中的美元符号、渲染公式容器并检查本地链接/资源。原图与出处由研究者准备。不要将模板占位符当成完成报告发布。

回归检查需要 Node.js，使用隔离临时副本验证代码中的美元符号、数学转义、公式配置、资源缺失和覆盖保护，并用已确认的完整报告核对全部数学内容没有丢失或串位。该检查不改写现有报告，不执行网络请求和发布。

## 发布与完成条件

1. 检查仓库 `AGENTS.md`、工作区和远端；同步最新分支，保护用户已有改动。只提交本任务文件。已有正确仓库时复用，不创建不相关站点。
2. 使用现有 GitHub 身份和系统凭据，不在文件、文档、命令参数或输出中保存 Token。受限网络导致 `gh auth status` 失败时，先在可联网环境验证 DNS/网络与认证，不能直接认定 Token 失效或要求重新提供。
3. 完成来源、公式、图片、链接、分类和样式检查；运行静态检查及 `git diff --check`。生成脚本不替代科学内容审查。
4. 在已授权的发布范围内提交、推送；核对远端 commit SHA 与本次提交一致。等待该 SHA 对应的 GitHub Pages 部署成功，不能用旧任务成功证明新部署成功。
5. 浏览线上报告，检查所有预期公式已渲染、无 `data-mjx-error`、所有原图已加载、正文与图注可读。延迟加载图片需滚动到相关章节后检查。桌面与窄屏检查页宽；公式/表格可独立滚动，整页不横向溢出。无浏览器条件时明确该验证限制。
6. 核对通信/其他父栏目 → 子栏目 → 文章的实际访问和必要入口，确认 HTTP 成功。输出简短说明和文章/栏目链接；有阻塞就区分“已完成、已提交、已推送、已部署、已线上验证”，不能合并成“已发布”。

内容完成标准是模型、方法和实验讲透且证据可查；样式完成标准是复用网站风格且正文可读；发布完成标准是新版本实际部署并验证。三者缺一不可。
